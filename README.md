# astrbot_plugin_bili_bridge · B站动态记忆桥

让 QQ 里的 AI 真正「看过」你在 B站 刷了什么，并且你追问某条视频讲了什么时，它会**现去拉字幕**再讲，而不是照抄摘要。

> 一句话：**B站 那边每天挑了什么 → 变成它的记忆；你问细节 → 它去 bili-cli 读字幕。**

---

## 前置依赖（先装好这三个，否则插件跑不起来）

| 依赖 | 作用 | 地址 |
| --- | --- | --- |
| **bili-cli**（pip 包 `bili-agent`，命令是 `bili`） | 本插件所有 B站 操作都走它：读私信、拉字幕、取视频信息。装完要 `bili auth login` 扫码登录。 | https://github.com/kukemc/bili-cli |
| **MemoryCompanion**（AstrBot 插件「我会牢牢记住你」） | 记忆写入靠它：把 B站 近况写进核心记忆块，每轮对话都会带上。没装的话同步功能会自动跳过。 | https://github.com/menglimi/astrbot_plugin_memory_companion |
| **刷B站插件 bili-scroll**（DSH 侧） | 负责挑片、写 `digest/YYYY-MM.md`、把推荐私信发给主人。没有它就没有「今天刷到什么」。 | https://github.com/c1overzz/dsh-bili-scroll |

装完这三个以后，**把下面这句话直接发给接了 AstrBot 的 AI**（她会自己体检、把该开的开关打开）：

> 请帮我验证 Astrbot 里的插件 B站动态记忆桥 的功能是否可用，并配置好。

> 🤖 **给 AI 看的**：收到这句话先读 [`SETUP-FOR-AI.md`](SETUP-FOR-AI.md)，
> 那里写了要改哪几个配置键、每个值为什么这么填、改完怎么验证（含端到端测私信转发的命令）。
> 这份手册和本 README 一起更新，照着做就能复现同样的效果。

配好之后你可以：

1. 把 B 站推的视频私信发到 QQ（有开关，默认关闭，**推荐打开**）
2. 给她分享 B 站视频，她会给你解析
3. 查看她最近刷到的视频
4. **在 QQ 上直接说一句「刷视频 / 刷B站 / 看视频」，她就真去刷一轮**——不用开面板、不用等你那个刷B站自己的时间窗。
   跑完的结果随 B 站那条私信推过来（一条，不会重复发）。

## 它做四件事

### 1. 记忆同步（后台，定时）

定时（默认 10 分钟）读取 B站 侧的挑选结果，压缩成一小段清单，写进 **MemoryCompanion 的核心记忆块**。核心块每轮对话都会无条件注入，所以「B站 今天看了什么」这类问题答得出来。

每一轮的块固定 **5 条**：

- 最新的 **2 条挑中并已私信**的视频（`block_picked` 可调）；
- 从这一轮**跳过**的视频里随机抽 **3 条**（`block_skipped` 可调）——这样问「最近看了什么」时，它能说出挑了什么、也放弃了什么，而不是只报几个标题。

**凑满 5 条**：这一轮不够 `block_picked + block_skipped`（默认 5）时，先拿当天更早的，还不够就从**前几天的挑片记录**里补，新的优先。所以哪怕今天只推了 2 条，问「今天看了什么」也还是 5 条。

**顺序统一**：刚推给主人的那批排在最前面，序号就是主人在 QQ 上看到的 1./2./3.；清单和「第几个视频」用的是同一份顺序，不会互相打架。

判断“这一轮”用 **BV 号**：没见过的才算新的。digest 文件会被写入端重排、改写，按行数差判断会漏掉最新的几条，所以不用行数。

每跑一轮，这一块整体替换成那一轮的内容；没有新 BV 时不重写，避免无谓的上下文变动。

**长期记忆**：除了这块会被覆盖的核心记忆，每一轮「挑中」的视频还会单独写一条带日期的长期记忆（按这一轮的 BV 集合去重，不会重复写）。所以过几天问「前两天推过什么」也查得到。

**历史搜索**：装了 `bili_search` 工具，可以按标题关键词、BV 号或日期去翻所有历史 digest 文件，不占记忆额度。

> 写入时机取决于 `sync_interval`（默认 600 秒）。想更贴近实时可以调到 120～300。

挑选结果的默认位置是 `~/.dsh/bili-duty/digest/YYYY-MM.md`（由刷视频类工具生成），每行格式：

```
2026-11-02 · BV1vynb6tEW5 · 标题 · UP主 · 值得看：一句理由 · https://www.bilibili.com/video/xxx
```

带「跳过」字样的行不会进记忆（可配置关键词）。

行首带 markdown 列表符号也认（`- ` / `* ` / `1. ` 都行），缩进无所谓——生成端常写成
`- 2026-11-02 · BV…`，插件会先把符号剥掉再解析。0.4.1 之前只认行首日期，遇到这种写法会
一行都匹配不上、同步静默跳过（日志里也看不到），踩过一次。

### 2. 按需解析（工具）

注册 LLM 工具 `bilibili_read(bvid)`：

- `bili video info` 取标题、UP、时长、播放/点赞/收藏/评论、简介；
- `bili video subtitle` 取字幕原文（截断到可配置上限）；
- 没字幕就退 `bili video summary`（B站 官方 AI 总结）；
- 同一个视频按 TTL 缓存（默认 1 小时），问两遍不重复跑。

### 3. 处理 QQ 分享卡片

QQ 的「分享视频」是 **JSON 卡片消息**：`message_str` 是空的，链接藏在卡片结构里，而且常常只有 `b23.tv` 短链。

插件会：把卡片内容整体取出来 → 正则找 BV 号 → 没有就跟随短链跳转解析出 BV → 给没有文字的消息补一段可读文字（不补的话 AstrBot 会判定消息无效，模型根本不会被叫起来）→ 在请求前把视频素材注入。

### 4. 说一句「刷视频」就真去刷一轮

在 QQ 上直接说 **「刷视频」「刷B站」「看视频」**（带不带「帮我/快/一下」都认），插件会：

1. **不替她说话**：插件只把「后台发生了什么」挂到这一轮请求上（一条临时说明，不落盘、不进上下文），
   措辞交给模型——所以她说「又来？才刚躺下」还是「行吧我去看看」是她自己的口气，不是插件塞的模板；
2. 转给 DSH 那边的**刷B站（`dsh-bili-scroll`）真跑一轮**——走它自己的 `POST /api/bili-duty/run`，所以冷却、跨宿主运行锁、当天额度那些规矩原样生效，这边**不复制一行业务逻辑**；
3. 等这一轮结束（盯 `duty.log` 里的「刷B站结束」）——**结果不自己发**：那一轮会把挑到的推给主人，
   私信转发会把它转过来，一条就够。插件只在这里记一笔日志。

> 这条说明也覆盖「没刷成」的几种情况（三分钟闸挡着 / 冷却里 / 上一轮还在跑 / 连不上 DSH），
> 模型知道发生了什么，就不会装作已经刷了，也不会编标题；
> **而且不允许它报具体秒数/分钟数**——「还要等 170 秒」那种一听就是机器。
> 想让插件省掉这次模型调用、直接回一句固定的话？把 `scroll_ack` 填上就行。

怎么连上 DSH 的（装的时候不用管，写在这里免得以后忘了）：DSH 的 Web 端每个进程会生成一个随机启动令牌，签名 cookie 的密钥落在
`~/.dsh/.credentials.yaml` 的 `client-connection/browser-session` 里。本机进程读得到，就照它的格式（`dsh-auth-<sha256(host:port)>` /
`v1.<payload>.<hmac>`）自己签一张去用；端口每次启动都变，所以拿 `netstat` 找出 `DeepSeek Harness` 正在监听的回环端口，再逐个拿 cookie 问一句
`/api/bili-duty/status`，回 `ok` 的那个才是它。**不依赖 psutil**（AstrBot 跑的那个 Python 里常常没有）。

配置项（都在插件设置页）：

| 键 | 默认 | 干什么 |
| --- | --- | --- |
| `scroll_enabled` | `true` | 总开关 |
| `scroll_owner_only` | `true` | 只认 `owner_uids` 里的人能触发（跑一轮要花额度） |
| `scroll_ignore_cooldown` | `true` | 刷B站在「手动轮冷却」里也照跑（见下） |
| `scroll_min_gap` | `180` | 两次口令之间至少隔几秒（默认三分钟） |
| `scroll_ack` | 空 | 空 = 让模型用自己的语气说（推荐）；填了 = 固定回这一句 |
| `scroll_report` | `false` | 跑完**自己**再发一条「刷完了，挑了 N 条」；默认关，结果走 B站 私信那条 |
| `scroll_report_max` | `5` | 最多报几条 |
| `scroll_wait_timeout` | `900` | 最多等多少秒 |
| `scroll_extra_words` | 空 | 额外的触发词，逗号分隔（例如「去溜溜」） |
| `dsh_gateway` | 空 | 手动指定网关地址；留空自动找 |

**刷B站正在冷却（`manualCooldownMin`）的时候怎么办？** 它自己的手滑保护是 10 分钟，撞上会回
「手动轮刚跑过，再等 N 分钟」。这边有两条路，都在插件里解决，不去改 DSH 的代码：

- **绕过（默认）**：临时把它的 `manualCooldownMin` 改成 `0`、开跑、**再把原值改回去**——全程只走它的
  配置接口 `POST /api/bili-duty/config`。读不到原值就**不绕**（宁可不跑，也不把人的设置搞丢）。
- **不绕**：`scroll_ignore_cooldown=false` 时这一轮就不跑，回一句「还得 N 分钟，回头再喊我」。

**拒绝就是拒绝。** 不管是「三分钟还没过」「上一轮还在跑」还是「冷却里没绕过去」，
插件都**不会**留个定时器过一会儿自己补跑——只有你再喊一次，它才会跑。
（这条是 2026-11-05 老大定的：拒绝了还偷偷去刷，看着就像它不听话。）

我们自己的那道闸是 `scroll_min_gap`（默认 **180 秒**，从**上一轮开跑**算）：三分钟内再喊，
这一轮不跑，她只会嫌你急。

**同一批视频只会推一遍。** 默认只发一条：B站 那边发给主人的私信（被转成「📬 B站 私信」）。
要是你把 `scroll_report` 打开了，插件会再发一条「刷完了，挑了 N 条」——那种情况下按 BV 去重，
半小时内同一批不再重复推（私信要等下一轮轮询才到，晚几十秒，看起来就像「又刷了一轮」）。

提醒一句：这一轮跑在 DSH 那边，用的是那边的账号额度与模型；`/bili_doctor` 里会多一行，专门告诉你「刷视频」这条路通不通。

## 安装与配置

1. 把本仓库放进 `AstrBot/data/plugins/`（或用插件市场安装）。
2. 重启 AstrBot，打开 WebUI → 插件 → **B站动态记忆桥**，填这几项：

| 配置项 | 说明 | 建议 |
| --- | --- | --- |
| `bili_executable` | bili-cli 可执行文件 | PATH 里有就写 `bili`，否则写绝对路径 |
| `digest_dir` | 挑选结果目录 | 留空 = `~/.dsh/bili-duty/digest` |
| `owner_uids` | 允许触发的 QQ 号（逗号分隔） | **必填**，否则任何人都能触发解析 |
| `memory_user_ids` | 记忆写到谁的记忆里 | 留空 = 沿用 `owner_uids` |
| `core_max_chars` | 核心块字数上限 | 默认 700；MemoryCompanion 全部核心块预算通常只有 800 字 |
| `detail_hint` | 写进记忆的用法提示 | 默认已包含「要分点讲、可以两三百字」 |

### 可选：把 B站 私信转到 QQ

> **这一项默认是关的，装完不会自己开始推。** 装完先想一下要不要：想收推荐私信就按下面三项打开；
> 不想收就留空跳过——插件启动时会打一行日志提醒「私信转发默认关闭」，`/bili_doctor` 也会标成 ❌ 让你确认一次。

先分清两个号，90% 的配置错误都出在这里：

| 角色 | 例子 | 在配置里是 |
| --- | --- | --- |
| **发信方**：登录着 bili-cli、负责把推荐私信发出去的号 | 1204686003「泡泡在加载」 | 不用填，插件用它自己发的消息（`dm_direction = me`） |
| **收信方**：被推荐的「主人」 | 1252860980「玩忽职守的月亮」 | 填进 `dm_owner_uid` |

也就是说：**你登录 bili-cli 的那个号 → 发给主人**，这批消息在会话里的 `from` 是 **`me`**（自己发的），所以默认 `dm_direction = me`。
如果反了（填了 `them`），插件会去等「主人发过来的消息」，推荐私信一条都不会转——看起来就像「配置好了但收不到」。

| 配置项 | 说明 |
| --- | --- |
| `dm_forward_enabled` | 打开转发（**默认 false**，必须手动打开） |
| `dm_owner_uid` | 收信方（对端）的 B站 UID，不是登录号自己 |
| `dm_target_session` | 转发到哪个 QQ 会话，形如 `qq-main:FriendMessage:1792559819`；留空会按平台真实 id 自动拼 |
| `dm_direction` | `me`（默认，转登录号自己发出去的）/ `them`（转对端发来的）/ `any`（都转） |
| `dm_poll_interval` | 轮询间隔，默认 180 秒 |
| `dm_mark_read` | 拉到之后是否在 B站 侧标已读，默认关 |

**拿不准用哪个方向**，看一条真实消息就行：

```powershell
bili dm read <dm_owner_uid> --limit 5
# 输出里每条有 "from": "me" 或 "them"，你要转的那批是哪种，dm_direction 就填哪种
```

排错顺序：`/bili_dm` 看状态（现在会直接写「方向 me —— 只转本机登录号自己发出去的」）→ `/bili_doctor` 看「私信转发」是不是 ❌ → 日志搜 `私信转发`，能看到「已记录基线 seqno=…（这批 me=3 条 / them=0 条，当前只转 me）」和「N 条私信 → QQ（共 M 次）」。

行为说明：**第一次运行只记录水位、不补发历史**；之后只推水位之后的新私信。发送失败不会推进水位，下一轮会重试——所以启动早期平台还没连上也不会丢消息。


### 关于「讲详细一点」

人设里常写「短句、1~3 句」，模型会严格执行，于是拿到 1800 字字幕也只回一句情绪话。所以本插件把「被问细节时可以讲 200~400 字、分 2~4 点」写进了 **核心记忆块** 和 **工具描述** 里，作为例外。

如果你不想要这个行为，清空 `detail_hint` 即可。

## 可选：语音转写（没有字幕时兜底）

**默认不装、不开，配置时由你决定要不要。**

它是干什么的：插件平时只读 B站 自己的字幕（CC 字幕 / AI 字幕）。这个可选功能是——
**当那条视频没有 B站 AI 字幕时**，用本机的语音识别把视频里说的话转成文字，再交给模型去讲。
不是识图 OCR，也不是云端服务，全在本机跑；有字幕的时候仍然优先用字幕（更准、更快）。

代价：要在本机部署 **ffmpeg**（抽音频）和 **一个语音识别模型**（sherpa-onnx + 中文模型），合计几百 MB；
第一次转写要十几秒到一两分钟（看时长），识别结果可能有错字、没有标点。

```powershell
# 装本机 ASR（有 4GB 以上 NVIDIA 显卡会自动用 GPU；国内建议带镜像参数）
bili asr setup local --device auto --model qwen3-asr --github-proxy https://gh-proxy.com/ --hf-mirror
bili asr status        # 看 ready 是不是 true

# 装好之后，把插件的这个开关打开（默认是关的）
#   transcribe_fallback: true
```

相关配置：`transcribe_fallback`（开关，默认关）、`transcribe_max_minutes`（只转前几分钟，默认 8）、
`transcribe_timeout`（超时秒数，默认 180）。

> **ffmpeg 没装怎么办**：`pip install imageio-ffmpeg`，再把它的 `ffmpeg.exe` 复制到 `bili.exe` 所在的
> `Scripts` 目录就行。插件会把 `bili.exe` 的目录自动加进子进程 PATH，所以不用去改系统环境变量。
> 实测：3 分钟的视频在 CPU 上转写约 8 秒（sensevoice 模型）。

**没装就保持关着**——插件会退回 B站 官方 AI 总结，不会报错；装完再打开即可。

## 「第一个视频讲了什么」按谁的顺序算？

**按「最近一次推给你的那批」的顺序算**，不是按记忆里那份清单。

原因：推送到 QQ 的那条私信里，三条视频是上游写好的 1./2./3.；而记忆块里的清单是
「挑中的几条 + 从跳过里随机抽几条」重新排过的。两份顺序本来就可能不一样，
拿记忆清单去解释「第一个」会答成另一条（2026-11 实测踩过，回了清单第一条而不是刚推的第一条）。

所以插件在转发私信时会把**这条消息里 BV 的出现顺序**记下来（`dm-state.json` 的 `pushBvs`），
之后「第几个视频」按它解析，并把对应那条的视频素材直接挂到这一轮请求上——
模型拿到的是你要的那条，而不是它自己从列表里数错的那条。

- 有效期：`ordinal_push_ttl_hours`（默认 12 小时）；过期就退回按记忆清单解释
- 找不到序号、或序号超出范围时，仍然走原来的清单逻辑
- 想确认当前记的是哪批：`/bili_dm` 只报转发状态；直接看 `dm-state.json` 的 `pushBvs` 最快

## 设计说明（关于提示词缓存）

用户直接分享视频链接时，插件**不会修改 `req.system_prompt`**。

系统提示词是提示词缓存的前缀，往里追加字幕（最多 6000 字）会让整段前缀失效，
每个带链接的请求都要重新 prefill，既费钱又拖慢首字。

所以素材是通过 `req.extra_user_content_parts` 追加的，并标记为**临时内容**
（`mark_as_temp()` / `make_as_temp()`），只对当轮可见、不写入会话上下文。
不带链接的普通对话完全不受影响，系统提示词保持逐字节稳定。

> 0.1.1 起修改。0.1.0 用的是 `req.system_prompt +=`，被插件市场以「破坏缓存命中率」驳回。

## 命令

- `/bili_sync` —— 立刻同步一次挑选结果（不等定时器）。
- `/bili_doctor` —— 体检：bili-cli、挑选结果、记忆、白名单、私信转发，以及「刷视频」那条路通不通。
- `/bili_dm on|off|status` —— 私信转发的开关。
- **口令（不用带 `/`）**：`刷视频` / `刷B站` / `看视频` —— 让她立刻去刷一轮。

## 常见问题

**Q：它答得出「今天看了什么」，但问细节时还是泛泛而谈。**
A：先看日志有没有 `Added llm tool: bilibili_read`；再看提问后有没有 `Agent 使用工具: ['bilibili_read']`。没有调用，多半是 `detail_hint` 被清空或改坏了。

**Q：提示「MemoryCompanion 未就绪」。**
A：没装或没启用 `astrbot_plugin_memory_companion`。插件其它功能（按需解析）不受影响。

**Q：同步一直接不到内容。**
A：先跑 `/bili_doctor`——它会报「文件里有几行可用、几行被忽略、第一条被忽略的长什么样」，还会带上一次同步的原因（「没有新的 BV」「内容没变」「MemoryCompanion 未就绪」都会写出来）。常见原因：`digest_dir` 指错、`skip_keyword` 把要的都过滤了、或者行格式变了。

**Q：拉不到字幕。**
A：bili-cli 没登录、或者视频本身没有字幕也没有官方总结。工具会如实返回「取不到」，不会编内容。

**Q：会被第三方服务看到我看什么视频吗？**
A：不会。所有请求都走本机 bili-cli，没有任何第三方解析接口。
